## 요약
Vite 기본 화면의 요소와 CSS를 모두 지우고 개인 개발 블로그의 뼈대를 만든다. 화면은 메뉴(헤더), 글 목록, 글 본문, 글쓰기 네 영역으로 나눈다.
새 의존성 없이 `App`의 `useState`로 "목록 / 본문 / 글쓰기" 화면을 전환한다. 데스크톱(768px 이상)에서는 목록과 본문을 나란히 보여주고, 모바일(768px 미만)에서는 한 번에 한 영역만 보여준다. 데이터는 코드에 넣은 예시 글을 쓴다.
범위는 위치 잡기까지다. 저장, 서버 연동, 디자인 다듬기는 하지 않는다.

## 개발자에게 확인할 질문
1. **화면 전환 방식**: 주소(URL)가 바뀌는 라우팅(react-router 등 새 의존성)이 필요한가, 아니면 상태 전환으로 충분한가?
   - 추천 답: 지금은 상태 전환으로 충분하다. 새로고침하면 목록 화면으로 돌아가는 제약은 받아들인다. 라우팅은 실제 글 데이터를 붙일 때 별도 기능으로 다룬다. 그때 뒤로가기 지원을 높은 우선순위로 잡는다(UX 검토 의견).
2. **배치**: 데스크톱과 모바일을 어떻게 배치할까?
   - 추천 답(UX 검토 후 수정):
     - 데스크톱(768px 이상, 1280px 기준): 헤더 메뉴 + 왼쪽 목록 사이드바 + 오른쪽 본문/글쓰기(B안).
     - 모바일(768px 미만, 375px 기준): **한 번에 한 영역만 보여준다.** `list`이면 목록만, `post`와 `write`이면 본문이나 글쓰기 화면만 보여준다. 본문 화면 맨 위에 "목록으로" 버튼을 둔다.
   - 바꾼 이유: 처음 추천한 "모바일에서는 목록 아래에 본문을 쌓는" 배치에서는 본문이 화면 밖에 나타난다. 그래서 글을 눌러도 아무 반응이 없는 것처럼 보인다(ux-review-1 [필수]).
3. **"CSS 다 비우기"의 범위**: 위치를 잡으려면 최소한의 레이아웃 CSS가 필요하다. 기존 내용을 모두 지운 뒤 레이아웃용 규칙(grid/flex, 간격, 포커스 표시, 모바일 영역 숨김)만 새로 넣어도 되는가?
   - 추천 답: 된다. `index.css`에는 기본 리셋 몇 줄만 남기고, `App.css`에는 레이아웃 규칙만 둔다. 색, 폰트, 장식은 넣지 않는다. 선택된 글을 굵게 표시하는 규칙 하나는 예외로 둔다(엣지 케이스 참고).
4. **기본 템플릿 자산 삭제**: `src/assets/hero.png`, `react.svg`, `vite.svg`, `public/icons.svg`를 삭제하고 `index.html`의 `<title>`을 바꿔도 되는가?
   - 추천 답: 쓰지 않게 되는 자산 4개는 삭제한다. `favicon.svg`는 남긴다. `<title>`은 "개발 블로그"로 바꾼다(블로그 이름이 정해져 있으면 알려 달라).
5. **글쓰기 화면의 저장 버튼**: 아직 저장 기능이 없는데 버튼을 어떻게 둘까?
   - 추천 답: 제목과 본문 입력칸, "저장" 버튼까지 배치만 한다. 버튼은 비활성(disabled)으로 둔다.
     - 입력칸 위에 "아직 저장할 수 없습니다. 입력한 내용은 화면을 벗어나면 사라집니다"라고 적는다.
     - 버튼 옆의 짧은 안내 "저장 기능은 준비 중입니다"는 `aria-describedby`로 버튼에 연결한다.
     - 눌렀는데 아무 일도 없는 버튼은 만들지 않는다.

- [ ] 모든 화면 상단에 블로그 이름(`h1`)과 메뉴("글 목록", "글쓰기")가 있는 헤더가 보인다.
- [ ] 헤더의 현재 위치 표시(`aria-current="page"`)는 `list`와 `post` 화면에서 "글 목록"에, `write` 화면에서 "글쓰기"에 붙는다.
- [ ] 처음 열면 글 목록이 보이고, 예시 글의 제목과 날짜(YYYY-MM-DD)가 최신순으로 나열된다.
- [ ] 목록에서 글 제목을 누르면 그 글의 제목, 날짜, 본문이 보이고, 포커스가 본문 제목(`h2`)으로 옮겨진다.
- [ ] 선택된 글의 목록 항목에는 `aria-current="true"`가 붙고 굵은 글씨로 표시된다. 색만으로 구분하지 않는다.
- [ ] 메뉴의 "글쓰기"를 누르면 입력칸 위의 저장 불가 안내, 라벨이 보이는 제목/본문 입력칸, 비활성 "저장" 버튼과 준비 중 안내가 보인다. 포커스는 글쓰기 제목(`h2`)으로 옮겨진다.
- [ ] 메뉴의 "글 목록"을 누르면 처음 화면(목록, 선택 없음)으로 돌아간다.
- [ ] 예시 글 배열이 비어 있으면 목록 영역에 "아직 글이 없습니다. 첫 글을 써보세요"와 글쓰기로 가는 버튼이 보인다.
- [ ] 데스크톱에서 글을 고르지 않았을 때 본문 영역에 "목록에서 읽을 글을 고르세요"가 보인다.
- [ ] 마우스 없이 Tab/Enter만으로 메뉴 이동, 글 선택, 글쓰기 진입, 목록 복귀가 모두 가능하고 포커스 위치가 보인다.
- [ ] 375px 폭에서 가로 스크롤이 생기지 않는다. 목록과 본문(또는 글쓰기)이 번갈아 한 화면씩 보이고, 본문 화면 맨 위의 "목록으로" 버튼으로 목록에 돌아간다. 헤더가 한 줄에 들어가지 않으면 줄이 바뀌고, 버튼은 모두 높이 44px 이상이다.
- [ ] 1280px 폭에서는 왼쪽에 목록, 오른쪽에 본문 또는 글쓰기가 동시에 보인다.
- [ ] `yarn lint`, `yarn build`, `yarn test`가 통과한다.

## 화면과 상태
데이터는 코드에 넣은 예시 글(동기 상수)이라 실제 로딩과 에러가 생기지 않는다. 그래서 로딩과 에러 화면은 이번 범위에서 만들지 않고, 데이터를 연결하는 기능에서 다룬다(엣지 케이스 E4 참고).

| 화면/영역 | 로딩 | 빈 상태 | 에러 | 정상 |
|---|---|---|---|---|
| 헤더(메뉴) | 해당 없음 | 해당 없음 | 해당 없음 | `h1` 블로그 이름, "글 목록", "글쓰기" 버튼. `list`와 `post`에서는 "글 목록", `write`에서는 "글쓰기"에 `aria-current="page"`. 좁은 폭에서는 줄바꿈 |
| 글 목록 | 해당 없음(정적 데이터) | "아직 글이 없습니다. 첫 글을 써보세요" + "글쓰기" 버튼 | 해당 없음 | 글 제목과 날짜(YYYY-MM-DD)를 최신순으로 나열. 선택된 글은 `aria-current="true"` + 굵은 글씨 |
| 글 본문 | 해당 없음 | 선택된 글이 없으면 "목록에서 읽을 글을 고르세요"(데스크톱 첫 화면에서만 보인다) | 선택한 id의 글이 없으면 "글을 찾을 수 없습니다" + 목록으로 돌아가기 버튼 | 맨 위 "목록으로" 버튼, 제목(`h2`, 포커스 대상), 날짜, 본문 텍스트 |
| 글쓰기 | 해당 없음 | 빈 입력칸(placeholder 안내) | 해당 없음 | 제목(`h2`, 포커스 대상), 입력칸 위 저장 불가 안내, 라벨이 붙은 제목/본문 입력칸, 비활성 "저장" 버튼 + `aria-describedby`로 연결된 준비 중 안내 |

모바일(768px 미만)에서 영역별로 보이는 것:

| `view` | 데스크톱 | 모바일 |
|---|---|---|
| `list` | 목록 + 본문 영역(선택 안내) | 목록만 |
| `post` | 목록 + 본문 | 본문만("목록으로" 버튼 포함) |
| `write` | 목록 + 글쓰기 | 글쓰기만 |

## 엣지 케이스
- [필수] 판단: 템플릿 자산을 지울 때 import가 남아 있으면 빌드가 깨진다. App.tsx의 asset import를 모두 지운 뒤 파일을 삭제한다.
  - 근거: `src/App.tsx` 2~4행이 `hero.png`, `react.svg`, `vite.svg`를 import하고, 37~107행이 `/icons.svg`를 참조한다.
  - 검토한 대안: 자산 파일을 남겨 두는 방법. 동작은 하지만 "요소 다 지워주고"라는 요청에 맞지 않아 택하지 않았다.
  - 확신도: 높음
  - 사람이 결정할 것: 자산 삭제 여부(질문 4)
- [필수] 판단: CSS를 완전히 비우면 목록/본문/글쓰기의 위치가 구분되지 않아 요청한 "위치 잡기"가 불가능하다. 레이아웃용 최소 CSS는 필요하다.
  - 근거: `docs/features/blog-layout/request.md`("css파일도 다 비워주고"와 "러프하게 위치 잡아주라"가 함께 있음)
  - 검토한 대안: 인라인 style 사용. CSS를 비웠다는 형식은 지키지만 실제로는 스타일이 옮겨 갈 뿐이고 반응형(미디어쿼리)을 할 수 없어 택하지 않았다.
  - 확신도: 중간
  - 사람이 결정할 것: 질문 3
- [필수] 판단: 모바일(768px 미만)에서는 `view`에 따라 한 영역만 보여준다. 레이아웃 컨테이너에 `data-view` 속성을 달고, 미디어쿼리 안에서 해당하지 않는 영역을 `display: none`으로 숨긴다. 본문 화면 맨 위에 "목록으로" 버튼을 둔다. 새 상태는 없다.
  - 근거: `docs/features/blog-layout/ux-review-1.md` [필수]. 세로로 쌓으면 본문이 화면 밖에 생겨서 누른 뒤 반응이 없는 것처럼 보인다(`docs/agents/ux-principles.md` 피드백 기준).
  - 검토한 대안:
    - 선택할 때 본문으로 자동 스크롤하는 방법은 코드가 더 복잡하고 목록으로 돌아가기도 불편해서 택하지 않았다.
    - JS로 화면 폭을 감지해 렌더링을 나누는 방법은 상태와 리스너가 늘어서 택하지 않았다. CSS 한 곳에서 처리하는 편이 위치 잡기 범위에 맞다.
  - 확신도: 높음
  - 사람이 결정할 것: 질문 2의 모바일 동작
- [권장] 판단: 메뉴와 목록 항목은 `<a href>`가 아니라 `<button type="button">`으로 만든다. 주소 이동이 없으니 링크를 쓰면 키보드, 스크린리더 사용자에게 잘못된 안내가 된다.
  - 근거: `docs/agents/ux-principles.md` 접근성 항목. 라우팅을 쓰지 않기로 한 질문 1의 추천 답. UX 검토에서도 타당하다고 확인했다.
  - 검토한 대안: `href="#"` 링크. 새로고침이나 뒤로가기를 했을 때 기대와 다르게 동작해서 택하지 않았다.
  - 확신도: 중간(질문 1에서 라우팅을 고르면 링크로 바꾼다)
- [권장] 판단: 글을 선택하거나 글쓰기에 들어가면 새로 나온 영역의 `h2`(`tabIndex={-1}`)로 포커스를 옮긴다.
  - `PostDetail`은 글이 있을 때만, `PostEditor`는 처음 표시될 때 `useEffect`와 ref로 `h2`에 포커스를 둔다.
  - `App`은 `<PostDetail key={selectedPostId}>`로 렌더링한다. 그래서 다른 글을 고를 때마다 다시 마운트되고 포커스가 옮겨진다.
  - 첫 화면(선택 없음)에서는 포커스를 옮기지 않는다.
  - 근거: `ux-review-1.md` [권장]. 모바일에서 목록 버튼이 숨겨지면 포커스가 문서 처음으로 튄다.
  - 검토한 대안: 아무것도 하지 않는 방법. 모바일 번갈아 표시와 함께 쓰면 키보드와 스크린리더 사용자가 길을 잃어서 택하지 않았다.
  - 확신도: 중간
- [권장] 판단: 선택된 글은 `aria-current="true"`와 굵은 글씨로 표시한다. 헤더의 `aria-current="page"`는 `list`와 `post`에서 "글 목록", `write`에서 "글쓰기"에 둔다.
  - 근거: `ux-review-1.md` [권장]. `ux-principles.md` "색만으로 정보를 전달하지 않는다". 색을 넣지 않는 이번 범위에서도 `font-weight` 규칙 한 줄로 해결된다.
  - 검토한 대안: 왼쪽 막대 표시는 장식에 가까워서 이번에는 넣지 않았다.
  - 확신도: 중간
- [권장] 판단: 375px에서 긴 영문 제목이나 코드 같은 긴 문자열이 가로 스크롤을 만들 수 있다. 본문 영역과 목록에 `overflow-wrap: anywhere`를 둔다.
  - 근거: 개발 블로그라 긴 영문 식별자가 많을 것으로 예상. `ux-principles.md` 반응형 기준 375px.
  - 검토한 대안: 이번에는 무시하는 방법. 규칙 한 줄로 막을 수 있어 넣는다.
  - 확신도: 중간
- [권장] 판단: 글쓰기 화면은 입력칸 위에 "아직 저장할 수 없습니다. 입력한 내용은 화면을 벗어나면 사라집니다"를 둔다. 비활성 버튼은 포커스를 받지 못하므로 버튼 옆 "저장 기능은 준비 중입니다"를 `aria-describedby`로 연결한다.
  - 근거: `ux-review-1.md` [권장] 1번과 [참고] 1번. 입력값은 비제어 입력이라 화면을 벗어나면 사라진다.
  - 검토한 대안: 화면을 벗어날 때 확인창을 띄우는 방법은 범위를 넘어서 택하지 않았다.
  - 확신도: 중간
- [참고] 판단: 모바일에서 "목록으로"나 헤더의 "글 목록"으로 돌아갈 때의 포커스 위치는 이번에 정하지 않는다. 목록은 데스크톱에서 항상 마운트되어 있어, 같은 방식(마운트 시 포커스)을 쓰면 첫 화면에서 포커스를 가져가 버린다.
  - 근거: 위 포커스 이동 판단. UX 검토는 선택과 글쓰기 진입만 다뤘다.
  - 검토한 대안: `view`가 `list`로 바뀔 때만 목록 `h2`에 포커스를 두는 방법. 이전 `view`를 비교하는 로직이 들어가서 이번에는 미뤘다.
  - 확신도: 낮음
  - 사람이 결정할 것: 이번 범위에 포함할지(포함하면 `App`에 작은 로직이 추가된다)
- [참고] 판단: 상태 전환 방식이라 새로고침하거나 뒤로가기를 하면 첫 화면(목록)으로 돌아간다. 이번 범위에서는 받아들인다. 라우팅 기능을 다룰 때 우선순위를 높게 잡는다.
  - 근거: 질문 1. `package.json`에 라우팅 라이브러리가 없음. `ux-review-1.md` [참고](꼼꼼한 사용자는 뒤로가기를 자주 쓴다).
  - 검토한 대안: `history.pushState`를 직접 다루는 방법. 위치 잡기 범위를 넘어서 택하지 않았다.
  - 확신도: 높음
- [참고] 판단(E4): 로딩과 에러 상태는 정적 데이터라 이번에 만들지 않는다. 데이터를 연결할 때 목록 영역에 추가한다.
  - 근거: CLAUDE.md "로딩, 빈 상태, 에러 상태를 항상 고려한다". 이번 기능에는 비동기 데이터가 없다. UX 검토에서도 타당하다고 확인했다.
  - 검토한 대안: 쓰이지 않는 가짜 로딩 UI를 미리 만드는 방법. 요청하지 않은 추가라서 택하지 않았다.
  - 확신도: 중간

## 구현 계획
새 의존성은 없다. 상태는 공통 부모인 `App`에 둔다(CLAUDE.md 규칙). 컴포넌트는 파일 하나에 하나씩, PascalCase 파일명으로 만들고 기능 폴더 `src/features/blog/`에 넣는다.

| 파일 | 작업 | 책임 |
|---|---|---|
| `src/App.tsx` | 전면 교체 | 상태 2개를 가진다. `view: 'list' \| 'post' \| 'write'`, `selectedPostId: string \| null`. 헤더와 `<main>`을 둔다. `<main>` 안의 레이아웃 컨테이너에 `data-view={view}`를 단다. 목록 영역과 본문/글쓰기 영역을 배치하고 전환 핸들러를 넘긴다. "글 목록"으로 이동하면 `view='list'`, `selectedPostId=null`로 바꾼다. 선택된 글은 id로 찾아 계산하고 상태에 따로 두지 않는다(`architecture.md`). `PostDetail`에는 `key={selectedPostId}`를 준다. |
| `src/App.css` | 비운 뒤 재작성 | 레이아웃 규칙만 둔다. 헤더 flex + `flex-wrap`. 768px 이상에서는 사이드바 + 본문 grid. 768px 미만에서는 한 열이고 `data-view`에 따라 목록 또는 본문 영역을 `display: none`으로 숨긴다. `:focus-visible` 외곽선, 버튼 최소 높이 44px, `overflow-wrap: anywhere`, 선택 항목(`[aria-current="true"]`)은 굵은 글씨. |

## 테스트 계획
- 단위 테스트: 이번 기능에는 로직이 있는 훅이나 유틸이 없다. 그래서 `architecture.md` 기준으로는 단위 테스트가 필수가 아니다. `yarn test`는 `--passWithNoTests`로 통과한다.
  - [참고] 화면 동작(메뉴 전환, 빈 상태, 포커스 이동)을 자동 테스트하려면 `@testing-library/react`와 `jsdom`이 필요하다. 현재 `package.json`에는 둘 다 없다. 새 의존성이라 이번 범위에서는 추가하지 않는다. 필요하면 개발자가 승인한 뒤 추가할 것을 제안한다.
- 사용 시나리오(qa-customer가 브라우저에서 확인):
  1. 1280px에서 처음 접속하면 기본 Vite 요소 없이 헤더, 왼쪽 글 목록, 오른쪽 "목록에서 읽을 글을 고르세요"가 보인다. 헤더 "글 목록"이 현재 위치로 표시된다.
  2. 목록에서 두 번째 글을 누르면 오른쪽에 그 글의 제목, 날짜, 본문이 보인다. 목록의 그 항목은 굵게 표시되고, 포커스는 글 제목에 있다.
  3. 헤더의 "글쓰기"를 누르면 입력칸 위의 저장 불가 안내, 입력칸 2개, 비활성 저장 버튼과 준비 중 안내가 보인다. 헤더 "글쓰기"가 현재 위치로 표시된다.
  4. 헤더의 "글 목록"을 누르면 처음 화면(선택 없음)으로 돌아간다.
  5. 375px에서 처음에는 목록만 보인다. 글을 누르면 본문만 보이고 맨 위에 "목록으로" 버튼이 있다. 그 버튼을 누르면 목록만 보인다. "글쓰기"를 누르면 글쓰기 화면만 보인다. 가로 스크롤이 없고, 헤더가 좁으면 줄이 바뀐다.
  6. 마우스 없이 Tab/Enter만으로 1~5를 반복할 수 있고 포커스 위치가 항상 보인다.
  7. (개발자 확인) `samplePosts`를 빈 배열로 바꾸면 빈 상태 안내와 글쓰기 버튼이 보인다.
- 정적 검증: `yarn lint`, `yarn build`, `yarn test`

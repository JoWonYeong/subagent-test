# UX 전체 검토 (1라운드)

**[필수] 1개, [권장] 4개, [참고] 3개**

기획안 전체를 검토했습니다. 범위가 러프한 위치 잡기라서 요구를 최소로 잡았습니다.

- [필수] 판단: 375px에서 "목록 아래에 본문이 오게 쌓는" 배치는 글을 눌러도 아무 반응이 없는 것처럼 보입니다. 모바일에서는 한 번에 한 영역만 보여주도록 바꾸세요.
  - 근거: `plan.md` 질문 2 추천 답("모바일에서는 목록 아래에 본문"), 완료 기준 "영역이 세로로 쌓인다", 테스트 시나리오 2와 3.
    - 예시 글이 3개뿐이어도 목록 아래 본문은 화면 밖에 있을 수 있습니다. 글이 늘어나면 더 심해집니다.
    - 급한 직장인(`docs/agents/personas.md`)은 안내문을 읽지 않고 여러 번 누릅니다. 글 제목이나 "글쓰기"를 눌러도 화면이 그대로인 것처럼 보입니다.
    - `ux-principles.md` 피드백 기준("행동에는 눈에 보이는 반응")에 어긋납니다.
  - 제안:
    - 768px 미만에서는 `view` 값에 따라 한 영역만 보여줍니다. `list`일 때는 목록만, `post`와 `write`일 때는 본문이나 입력 화면만 보입니다.
    - `post` 화면 상단에 "목록으로" 버튼을 둡니다. 새 상태 없이 기존 `view` 값으로 처리됩니다.
    - 데스크톱 B안(목록 + 본문 동시 표시)은 그대로 둡니다.
    - 완료 기준 "영역이 세로로 쌓인다"는 "모바일에서는 목록과 본문이 번갈아 한 화면씩 보인다"로 바꿉니다.
  - 검토한 대안:
    - 선택 시 본문으로 자동 스크롤하는 방법은 코드가 더 복잡하고 스크롤 후 돌아가기도 불편합니다.
    - 모바일 쌓기를 유지하는 방법은 위 문제가 남아 택하지 않았습니다.
  - 확신도: 높음
  - 사람이 결정할 것: 질문 2의 모바일 동작을 "번갈아 표시"로 바꿀지 결정해야 합니다.

- [권장] 판단: 글쓰기 화면에서 "준비 중" 안내를 입력칸 위에 두고, 입력한 내용이 저장되지 않는다는 점도 함께 적으세요.
  - 근거: `plan.md` 질문 5와 `PostEditor.tsx` 항목.
    - 안내가 저장 버튼 옆(입력칸 아래)에 있습니다.
    - 입력값은 비제어 입력이라 목록으로 이동하면 사라집니다.
    - 처음 쓰는 사용자와 꼼꼼한 사용자(personas.md)는 긴 글을 쓴 뒤에야 저장이 안 되는 것을 알게 됩니다.
  - 제안: 화면 상단에 "아직 저장할 수 없습니다. 입력한 내용은 화면을 벗어나면 사라집니다"처럼 적습니다. 저장 버튼 옆의 짧은 안내는 그대로 둬도 됩니다.
  - 검토한 대안: 이탈 시 확인창을 띄우는 방법은 이번 범위를 넘어서 택하지 않았습니다.
  - 확신도: 중간

- [권장] 판단: 빈 본문 영역 문구 "왼쪽 목록에서 읽을 글을 고르세요"는 모바일에서 틀린 말이 되므로 "목록에서 읽을 글을 고르세요"로 바꾸세요.
  - 근거: `plan.md` 화면과 상태 표의 글 본문 행. 모바일에는 "왼쪽"이 없습니다. 위 [필수]처럼 번갈아 표시하면 모바일에서는 이 문구 자체가 보이지 않을 수 있습니다.
  - 검토한 대안: 폭에 따라 문구를 둘로 나누는 방법은 과해서 택하지 않았습니다.
  - 확신도: 높음

- [권장] 판단: 화면이 바뀔 때의 포커스 이동을 정하세요. 글 제목을 누르거나 "글쓰기"를 누르면 새로 나온 영역의 제목(`h2`, `tabIndex={-1}`)으로 포커스를 옮깁니다.
  - 근거: `plan.md` 완료 기준 "Tab/Enter만으로 이동 가능". 모바일에서 목록 버튼이 사라지면 포커스가 문서 처음으로 튑니다. 스크린리더는 화면이 바뀐 것을 알 수 없습니다. `ux-principles.md` 접근성 항목("포커스 위치가 항상 보여야 한다")에 해당합니다.
  - 검토한 대안: 아무것도 하지 않는 방법은 데스크톱 B안에서는 큰 문제가 없지만, 모바일 번갈아 표시에서는 문제가 됩니다.
  - 확신도: 중간

- [권장] 판단: 선택된 글 표시는 색만으로 하지 말고 `aria-current="true"`와 굵은 글씨나 왼쪽 막대 같은 모양 차이를 함께 쓰세요. 헤더의 "글 목록"이 `post` 화면에서도 현재 위치로 표시되는지 정하세요.
  - 근거: `plan.md` 화면과 상태 표("선택된 글에 표시"). 방식이 정해져 있지 않습니다. `ux-principles.md` "색만으로 정보를 전달하지 않는다". `view=post`일 때 `aria-current`를 어느 메뉴에 둘지도 빠져 있습니다.
  - 제안: `list`와 `post`는 "글 목록", `write`는 "글쓰기"에 표시합니다.
  - 확신도: 중간

- [참고] 판단: 저장 버튼이 `disabled`이면 키보드 포커스를 받지 못해 스크린리더가 "준비 중" 안내를 놓칠 수 있습니다. 안내문을 `aria-describedby`로 연결하거나 버튼 바로 앞에 텍스트로 두면 됩니다.
  - 근거: `plan.md` 질문 5.
  - 확신도: 중간

- [참고] 판단: 기본 구조(`h1` 블로그 이름, `main`, 영역별 `h2`)와 날짜 형식(예: 2026-11-20)은 구현 때 맞춰 두면 좋습니다. 375px에서 헤더의 블로그 이름과 메뉴 두 개가 한 줄에 안 들어가면 줄바꿈되도록 합니다. 이때도 각 버튼은 44px 이상으로 둡니다.
  - 근거: `plan.md` `BlogHeader.tsx` 항목, `ux-principles.md` 반응형 항목.
  - 확신도: 낮음

- [참고] 판단: 기획안의 다음 결정은 UX 관점에서 타당합니다.
  - 로딩과 에러 상태를 만들지 않는 것은 정적 데이터라서 맞습니다.
  - 메뉴와 목록 항목에 `<button>`을 쓰는 것은 라우팅이 없어서 맞습니다.
  - 빈 상태의 안내와 글쓰기 버튼, 비활성 저장 버튼, `overflow-wrap`, `:focus-visible`, 44px 터치 영역도 적절합니다.
  - 새로고침하면 목록으로 돌아가는 제약은 이번 범위에서는 괜찮습니다. 다만 꼼꼼한 사용자(뒤로가기를 자주 함)가 걸릴 수 있으니 라우팅 기능을 따로 다룰 때 우선순위를 높게 잡으세요.
  - 확신도: 높음

너는 이 작업의 **진행자(메인)**다. 아래 흐름을 순서대로 진행한다.
서브에이전트에게 일을 맡기고, 결과를 파일로 저장하고, 개발자의 승인을 받는다.

요청: $ARGUMENTS

## 준비
1. 요청에 맞는 짧은 영문 slug를 정한다 (예: `todo-filter`).
2. `docs/features/<slug>/` 폴더를 만든다.
3. 요청 원문을 `docs/features/<slug>/request.md`에 저장한다.
4. 아래 진행 기록을 `docs/features/<slug>/log.md`에 만들고, 단계가 끝날 때마다 한 줄씩 추가한다.

```markdown
# <slug> 진행 기록
| 단계 | 에이전트 | 결과 요약 | 파일 |
|---|---|---|---|
```

## 1단계: 기획 (1라운드)
1. `planner`를 **최초 기획** 모드로 호출한다. `request.md` 경로를 넘긴다.
2. 결과 원문을 `plan.md`로 저장한다.

## 2단계: UX 전체 검토 (1라운드)
1. `ux-designer`를 **기획안 전체 검토** 모드로 호출한다. `plan.md` 경로를 넘긴다. 요약해서 넘기지 않는다.
2. 결과 원문을 `ux-review-1.md`로 저장한다.
3. **종료 조건 ①**: [필수] 항목이 0개면 3단계, 4단계를 건너뛰고 5단계로 간다.

## 3단계: 기획 수정
1. `planner`를 **UX 의견 반영** 모드로 호출한다. `plan.md`, `ux-review-1.md` 경로를 넘긴다.
2. 결과 원문으로 `plan.md`를 덮어쓴다. 수정 전 버전은 `plan-v1.md`로 보관한다.

## 4단계: UX 필수 항목 확인 (2라운드, 마지막)
1. `ux-designer`를 **필수 항목 확인** 모드로 호출한다. `plan.md`, `ux-review-1.md` 경로를 넘긴다.
2. 결과 원문을 `ux-review-2.md`로 저장한다.
3. **종료 조건 ②**: 결과와 상관없이 기획-UX 의논은 여기서 끝낸다. 3라운드는 없다.
4. **종료 조건 ④**: 미해결 [필수] 항목이 남아 있으면, 에이전트를 다시 부르지 않고 5단계의 "내가 결정할 것"에 기획과 UX 양쪽 의견을 나란히 적는다.

## 5단계: ✋ 개발자 승인 (반드시 멈춘다)
`plan.md` 맨 위에 아래 섹션을 추가하고, 같은 내용을 개발자에게 보여준다.

```markdown
## 🧭 승인 요청 요약
- 의논 라운드: 1 또는 2
- 합의된 핵심 내용: (3~5줄)

### ❓ 내가 결정할 것
| 주제 | 기획 의견 | UX 의견 | 메인 제안 |
|---|---|---|---|

### 기획의 질문 (추천 답 포함)
1. ...

### 그 밖의 [권장] / [참고] (반영 여부 선택)
- ...
```

**개발자가 승인하기 전에는 절대 구현을 시작하지 않는다.** 개발자의 답과 결정은 `plan.md`의 "결정 사항" 섹션에 기록한다.

## 6단계: 구현 (메인이 직접)
1. 승인된 `plan.md`의 구현 계획을 따른다. 계획에 없는 파일이나 기능을 추가하지 않는다.
2. 계획과 다르게 해야 할 이유가 생기면 멈추고 개발자에게 묻는다.
3. 작은 단위로 나눠서 진행한다. 린트는 PostToolUse hook이, lint·build·test 전체는 Stop hook이 자동 실행하므로 직접 다시 실행하지 않는다.
4. 구현이 끝나면 `implementation.md`에 아래를 기록한다.
   - 변경한 파일별로 무엇을, 왜 바꿨는지
   - **내가 임의로 판단한 부분** (기획안에 없어서 스스로 정한 것)
   - **확신이 없는 부분**

## 7단계: 검증 (동시 실행)
1. QA를 위해 dev 서버를 백그라운드로 실행하고 URL을 확인한다 (`yarn dev`).
2. 아래 두 에이전트를 **동시에** 호출한다.
   - `code-reviewer`: `plan.md`, `implementation.md` 경로와 "기계 검사는 hook으로 통과함"을 넘긴다.
   - `qa-customer`: URL, `plan.md`의 완료 기준, `docs/agents/personas.md`의 고객 유형을 **고객의 말로** 넘긴다. 코드나 구현 방식은 알려주지 않는다.
3. 화면이 있는 기능이면 `ux-designer`를 **구현된 화면 검토** 모드로 호출한다 (URL 전달).
4. 결과 원문을 각각 `review.md`, `qa.md`, `ux-review-final.md`로 저장한다.
5. 검증이 끝나면 dev 서버를 종료한다.

## 8단계: ✋ 개발자 판단 (반드시 멈춘다)
`report.md`를 만들고 개발자에게 보여준다.

```markdown
# <slug> 최종 보고

## 한눈에 보기
- 기계 검사: lint / build / test 결과
- 코드 리뷰: [필수] N, [권장] N, [참고] N
- QA: 완료 기준 N/M 통과, 문제 [필수] N
- UX 화면 검토: [필수] N

## 반드시 고칠 것 ([필수] 전체)
| 출처 | 문제 | 위치 | 제안 |
|---|---|---|---|

## 고칠지 선택할 것 ([권장])
| 출처 | 문제 | 제안 |
|---|---|---|

## 메인이 임의로 판단한 부분 (확인 필요)
- ...
```

개발자가 고칠 항목을 고르면 그것만 수정하고, 수정 후 `code-reviewer`를 **수정한 항목 확인** 범위로만 다시 호출한다 (QA 재실행은 개발자가 요청할 때만).
수정-재확인은 **최대 2회**다. 그래도 남은 항목은 에이전트를 다시 부르지 않고 개발자에게 넘긴다.
개발자가 승인하면 `/pr`로 PR을 만든다.

## 공통 원칙
- 서브에이전트의 결과를 **요약해서 다음 에이전트에게 넘기지 않는다.** 항상 파일 경로를 넘긴다.
- 서브에이전트끼리의 의논은 **최대 2라운드**다. 그 이상은 개발자가 결정한다.
- 토큰을 아낀다: 서브에이전트에게는 필요한 파일 경로만 넘기고, 재호출 시에는 확인할 범위를 좁혀서 넘긴다.
- 각 단계가 끝날 때마다 `log.md`에 한 줄을 추가한다.
- 개발자에게 보여주는 메시지는 짧게 하고, 자세한 내용은 파일 경로로 안내한다.
